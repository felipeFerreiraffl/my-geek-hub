# Repo-wide Conventions

These apply across the whole repository. Package-specific conventions live in
[../backend/conventions.md](../backend/conventions.md) (and, eventually, a
frontend equivalent).

## Language

All code, code comments, commit messages, and documentation are written in
**English**, regardless of the language used in discussion or planning.

## Version control

**Commit messages** follow [Conventional Commits](https://www.conventionalcommits.org/):

```
feat: new routes for bookmarks
fix(package): fix on drizzle and build dependencies
chore(index): changed default PORT of localhost operation
docs: map existing codebase
refactor: new structure of folders
```

Common types in use: `feat`, `fix`, `chore`, `docs`, `refactor`. An optional scope
in parentheses names the affected area (e.g. `feat(users): ...`).

**Branching:**

- Feature work happens on `feature/<scope>` branches (e.g. `feature/backend-bookmarks`).
- Feature branches merge into `develop`.
- `develop` merges into `main` for releases.

## Repository layout

- `backend/` and `frontend/` are independent Node.js projects — each has its own
  `package.json`, lockfile, and `tsconfig.json`. There is no npm/yarn workspace or
  monorepo build tool (Turborepo, Nx, etc.) tying them together.
- Both projects use the same TypeScript path-alias convention: `@/*` maps to that
  project's `src/*`.
- `docs/` holds hand-maintained documentation, split into `general/`, `backend/`,
  and (once code exists) `frontend/`.
- `.planning/` holds GSD workflow artifacts, including an automated, point-in-time
  codebase analysis under `.planning/codebase/`. That analysis is regenerated by
  tooling and is a reference/snapshot — `docs/` is the maintained source of truth.

## Environment & secrets

- Each app that needs configuration loads it from its own `.env` file (not
  committed — see `.gitignore`).
- The backend validates its environment with a Zod schema at startup; see
  [../backend/stack.md](../backend/stack.md) for the required variables.
