# Backend architecture

Explanation of how the `backend/` folder is organized and why each part exists. For how the backend talks to the frontend and the external APIs, see the [general architecture](../architecture.md).

## Shape

```txt
backend/
├── src/
│   ├── api/            Features: CRUDs and reverse proxies
│   ├── config/         Setup of database, env vars, rate limits and proxy probes
│   ├── constants/      Fixed values used across the project
│   ├── db/
│   │   └── drizzle/
│   │       └── schemas/   One file per table
│   ├── libs/           Helpers for external libraries (JWT)
│   ├── middlewares/    Functions that run between the request and the controller
│   ├── types/          General TypeScript types
│   ├── utils/          Generic helper functions
│   ├── app.ts          Express app: middlewares and routes
│   └── index.ts        Server startup
├── drizzle/            Migrations generated by Drizzle Kit
├── drizzle.config.ts
├── package.json
└── tsconfig.json
```

## `src/`

The main code of the backend. Everything that runs on the server lives here.

### `api/`

The core logic of the API. It is organized by **feature**: each folder is one area of the app (`auth`, `users`, `bookmarks`, `ratings`), and each feature splits its work into layers.

```txt
routes → controller → service → database
```

| File                      | Responsibility                                                           |
| ------------------------- | ------------------------------------------------------------------------ |
| `<feature>.routes.ts`     | Defines the paths and which middlewares run on each one.                 |
| `<feature>.controller.ts` | Reads the request, calls the service and sends the response.             |
| `<feature>.service.ts`    | Business logic and database queries. Knows nothing about `req` or `res`. |

```txt
api/bookmarks/
├── bookmarks.routes.ts
├── bookmarks.controller.ts
└── bookmarks.service.ts
```

**Why layers?** Each file has only one job. A service can be reused by other controllers (e.g. `ratings` uses `BookmarkService` to check if a bookmark exists), and a route can change its middlewares without touching the business logic.

#### Proxy

`api/proxy/` is the exception to the layers above. It doesn't store anything, it only forwards the request to an external API, so it has **no controller or service**.

```txt
api/proxy/
└── tenrai/                    Target: the external API
    ├── tenrai.proxy.ts        Proxy factory (URL, headers, cache)
    ├── tenrai.helpers.ts      Path helpers shared by its scopes
    ├── animes/                Scope: the media type
    │   └── animes.routes.ts   Routes mounted at /api/animes
    └── mangas/
        └── mangas.routes.ts   Routes mounted at /api/mangas
```

- **Target** → the external API (e.g. `tenrai`). Its `<target>.proxy.ts` holds the shared setup for every scope.
- **Scope** → a media type inside the target (e.g. `animes`). Its `<scope>.routes.ts` maps local paths to the external API paths.

New scopes are added with the `proxy-route` skill.

### `config/`

Files that **prepare** something before the app uses it.

| File           | Content                                                            |
| -------------- | ------------------------------------------------------------------ |
| `db.ts`        | Database client and connection check on startup.                   |
| `dotenv.ts`    | Validates the env vars with Zod. The app stops if any is invalid.  |
| `rateLimit.ts` | Rate limiters, following the official limits of each external API. |
| `proxy.ts`     | Probes that test each external API on startup (dev only).          |

### `constants/`

Fixed values used in more than one place, like external API URLs (`api.ts`), HTTP status messages (`status.ts`), expiration times and rating limits (`numbers.ts`) and the validated env vars (`dotenv.ts`).

### `db/`

The database structure, built with Drizzle ORM.

- `drizzle/schemas/` → one file per table (`users`, `bookmarks`, `ratings`, `auth`).
- `drizzle/relations.ts` → how the tables relate to each other (e.g. a user has many bookmarks).
- `drizzle/index.ts` → exports every schema in one place, so Drizzle Kit and the services can find them.

### `libs/`

Setup and helpers that are specific to an **external library**. Today it has `jwt.ts`, which wraps `jose` to sign and verify tokens. If the library changes, only this folder changes.

### `middlewares/`

A **middleware** is a function that runs _between_ receiving the request and reaching the controller. It can check something and let the request continue (`next()`), or stop it and send an error (`next({ status })`).

```txt
request → authenticateUser → authorizeAdminOnly → controller → response
                 │                    │
                 └── 401 ─────────────┴── 403 ──▶ errorHandler
```

| File                        | Content                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `auth.middleware.ts`        | Reads the JWT token (`authenticateUser`) and checks the role (`authorizeAdminOnly`, `authorizeSelfOrAdmin`). |
| `validation.middleware.ts`  | Validates the request body with Zod (e.g. email and password).                                               |
| `handleError.middleware.ts` | Last middleware of the app. Turns every error into the same JSON response.                                   |

### `types/`

General TypeScript types of the project: database models (`db.types.ts`), JWT payload (`auth.types.ts`), errors (`status.types.ts`) and the `req.user` extension for Express (`express.d.ts`).

- Schemas and types used by both apps (e.g. `emailSchema`, `passwordSchema`, external API responses) live in the root `shared/` folder, imported with `@shared/*`.
- Backend-only Zod schemas don't live here: they stay next to the code that uses them (e.g. `envSchema` in `config/dotenv.ts`).

### `utils/`

Small and generic functions, not tied to a feature.

| File          | Content                                                                               |
| ------------- | ------------------------------------------------------------------------------------- |
| `logger.ts`   | Pino loggers with a prefix (`logger`, `authLogger`, `databaseLogger`, `proxyLogger`). |
| `messages.ts` | `successRes()`, the standard success response.                                        |
| `serverFn.ts` | Wrappers for handlers (`asyncFn`, `middlewareFn`) and password hashing.               |

### `app.ts` and `index.ts`

The app is split in two files on purpose:

- `app.ts` → **what** the server does: Express setup (`helmet`, JSON), routes and the error handler.
- `index.ts` → **how** it starts: connects to the database, runs the proxy probes and opens the port, printing the server info on the console.

This way, `app` can be imported without starting a server (e.g. in tests).

## `drizzle/`

Migrations generated by Drizzle Kit from the schemas in `src/db/drizzle/`. Each `.sql` file is one change to the database, and `meta/` keeps the snapshots Drizzle uses to compare versions. These files are generated, not written by hand.

```bash
npm run db:generate   # create a migration from schema changes
npm run db:migrate    # apply the migrations
npm run db:push       # sync the schema directly (dev only)
npm run db:studio     # open Drizzle Studio
```
